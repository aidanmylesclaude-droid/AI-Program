# 3.1 Settings, permissions and security hardening
**Stage / Module:** 3 · **Status:** done · **Date taught:** 2026-11-20
**Builds on:** 1.1.6–1.1.8 (settings files), 1.2.5 (permission modes), 1.5.2 (`.env`), 1.6.4 (guardrails in code).
**Source:** code.claude.com/docs/en/permissions, checked 2026-11-20.

## What you'll learn
How to make Claude Code *unable* to do certain things on your PC (not just asked not to), and the limits of that.

## Key terms
- **Permission rule:** a line in a settings file saying a tool use is `allow`ed, `ask`ed about, or `deny`ed.
- **Deny wins:** rules are checked deny → ask → allow; "an allow rule can't carve an exception out of a deny rule" (docs).
- **Enforced vs advice:** the docs: "Permission rules are enforced by Claude Code, not by the model. Instructions in your prompt or CLAUDE.md shape what Claude tries to do, but they don't change these rules."
- **Gitignore-style path pattern:** the same matching style as `.gitignore` (1.3.4). `**` = any folders. On Windows, `//**/.env` = a `.env` file anywhere on any drive.
- **Defense in depth:** several layers, so one failing isn't a disaster (`.gitignore` + deny rule + CLAUDE.md rule + fake keys in practice).

## The problem this solves
Your "never read `.env`" rule lives in CLAUDE.md: advice the model *usually* follows. A deny rule makes it a hard rule the program enforces, even if a prompt injection (1.6.4) talks the model into trying.

## Explanation
**Where settings live** (narrow beats broad, 1.1.7): user `~\.claude\settings.json` (all your projects) → project `.claude\settings.json` (shared, committed) → `.claude\settings.local.json` (yours, git-ignored). Deny rules from any level apply.

**The change (user settings, so every project is protected):**
```json
"permissions": {
  "deny": ["Read(//**/.env)", "Read(//**/.env.*)"],
  "disableBypassPermissionsMode": "disable"
}
```
- The two `Read` denies block Claude's file tools from reading *or* editing any `.env` file (docs: a Read deny "also blocks the Edit and Write tools on the same path").
- `disableBypassPermissionsMode` removes Bypass mode entirely (1.2.5: never on your PC).

**Honest limits (from the docs):** deny rules cover Claude's built-in file tools and shell commands Claude Code can analyse (like `cat`). They "don't apply to … arbitrary subprocesses that read or write files indirectly, like a Python or Node script". So a deny rule is a strong layer, not a wall: real secrets still belong only in `.env`, never in notes, and keys get revoked if leaked. The OS-level wall is the **sandbox** (later, Stage 5).

## Example from your projects
The trading agent's future data-API key sits in its project's `.env`. With this rule, no Claude Code session in any project can open it with its file tools, even one tricked by a web page.

## Hands-on exercise (your approval, then Claude runs it)
Claude adds the rule to user settings, then tries to read the **fake** key file `sandbox-1.5.2\.env` two ways: (1) the Read tool, (2) a PowerShell `Get-Content` command.
**Predict:** which of the two gets blocked?

## Knowledge check (2 questions)
1. CLAUDE.md says "never read .env" and a deny rule says the same. What's the difference?
2. Name one thing the deny rule does *not* stop.

## Concept notes created or updated
None.

## Answers
- Result (tested 2026-11-20): **both blocked**. Read tool: "denied by your permission settings". PowerShell `Get-Content`: "was blocked" (message mentioned working directories, but the read did not happen). Rules applied immediately, no restart.
1. CLAUDE.md is advice the model can fail to follow; the deny rule is enforced by Claude Code itself, whatever the model tries.
2. A script (e.g. Python) that opens the file itself; or a command that reads files without naming them. (Hence secrets only in `.env`, and sandboxing later.)
