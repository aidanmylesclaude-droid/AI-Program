## What you'll learn
- What a package is, and where `pip` gets packages from
- Why every project gets its own **virtual environment**
- How to use one on Windows **without** changing any security settings
- How a `requirements.txt` file lets you rebuild an environment anywhere

## Key terms
- **Package (library):** code someone else wrote that you `import`, e.g. `requests` for talking to websites and APIs. Python's built-in tools (`random`, `collections`) need no install; packages do.
- **PyPI:** the Python Package Index (pypi.org), the official public store `pip` downloads from. Anyone can publish there.
- **pip:** the tool that installs packages. Run it as `python -m pip ...` so it's clear *which* Python it installs into.
- **Virtual environment (venv):** a private folder (by convention `.venv`) with its own copy of Python's package area. Packages installed there are visible only to that project.
- **Activate:** a shortcut that makes `python` mean "this venv's Python" for the current window. Optional (see below).
- **`requirements.txt`:** a plain list of a project's packages and exact versions, so the environment can be rebuilt.
- **Typosquatting:** a fake package with a name one letter off a real one (e.g. `reqeusts`), uploaded to trick people. It's a known supply-chain risk.

## The problem this solves
Your trading assistant might need version 2 of a charting library while the content agent needs version 3. If both install into the *same* global Python, one breaks the other. A venv per project keeps them apart. It's the same "one folder, its own settings" idea as 1.1.8, applied to code.

## Explanation
```
global Python (py)            ← keep clean: no project packages here
trading-research\.venv\       ← requests, pandas … for trading only
content-agent\.venv\          ← its own packages and versions
```
**Create:** `py -m venv .venv` (inside the project folder).
**Use without activating** (what we'll do): call the venv's own Python by its path:
- `.venv\Scripts\python.exe -m pip install requests`
- `.venv\Scripts\python.exe my_script.py`
The docs: "You don't specifically need to activate a virtual environment, as you can just specify the full path to that environment's Python interpreter." It's explicit, works in any window, and is what agents usually do.

**About activating:** `.venv\Scripts\Activate.ps1` is a script, and Windows PowerShell blocks scripts by default. The docs suggest changing the *execution policy* to allow it. That's a security setting; we don't need to change it, so we won't.

**Never commit the venv.** The docs call venvs "disposable" and "not checked into source control". Since Python 3.13, `venv` even puts its own `.gitignore` inside `.venv`. Commit `requirements.txt` instead, then rebuild with `.venv\Scripts\python.exe -m pip install -r requirements.txt`.

**Installing safely**
1. Install only packages you've decided you need (an Optimization Center review for anything non-trivial).
2. Type the **exact** name; check it on pypi.org (description, maintainers, how widely used).
3. Install into the project's venv, never the global Python.
4. A package is code you'll run, so the 1.1.6 and 1.4.1 rules apply.

## Example from your projects
`trading-research\` gets: `.gitignore` (with `.env` and `.venv/`), `py -m venv .venv`, then `.venv\Scripts\python.exe -m pip install requests` for the market-data API (1.5.1). `requirements.txt` records `requests==<version>`. On a new PC: clone, create `.venv`, `pip install -r requirements.txt`, add `.env` by hand.

## Hands-on exercise
In a new `exercises\sandbox-1.4.2`. Each step is one line.
1. `cd ~\AI-Program\01-University\exercises; mkdir sandbox-1.4.2; cd sandbox-1.4.2; py -m venv .venv`
2. Predict, then: `py -c "import requests"` (the global Python)
3. `.venv\Scripts\python.exe -m pip install requests` (downloads from PyPI)
4. `.venv\Scripts\python.exe -c "import requests; print(requests.__version__)"`
5. Predict, then run step 2 again
6. `.venv\Scripts\python.exe -m pip freeze | Set-Content requirements.txt; cat requirements.txt`
7. Predict, then: `git status --short` (does `.venv` appear?)
