# 1.3.4 `.gitignore` and keeping secrets out of history
**Stage / Module:** 1 / 1.3 · **Status:** done · **Date taught:** 2026-11-19
**Builds on:** 1.1.5 (`.env` holds secrets as plain text), 1.3.2 (history keeps everything), 1.3.3 (a pushed secret is leaked; revoke it).
**Rehearsed:** every step was run by Claude in a throwaway repo first (Git 2.56.1).

## What you'll learn
- How to tell Git to never track certain files
- How to check *why* a file is ignored
- The trap: `.gitignore` doesn't help with a file Git is *already* tracking
- What to do if a secret was committed

## Key terms
- **`.gitignore`:** a plain-text file in the repo listing names or patterns Git should ignore. Each line is one rule.
- **Ignored:** Git acts as if the file isn't there. It won't show it in `status`, and `git add .` skips it.
- **Tracked:** a file Git already has in its history. `.gitignore` does **not** apply to tracked files.
- **Pattern:** a rule that matches several names. `*.log` means "any file ending in `.log`". `.env*` means "anything starting with `.env`".
- **`git rm --cached <file>`:** stop tracking a file but **keep it on disk**.
- **`HEAD~1`:** "one commit before the latest".
- **Revoke:** cancel a key at the service that issued it, so it stops working. Then you create a new one.

## The problem this solves
Your trading assistant will need a market-data API key, and your content agent will need platform keys. They live in `.env` (1.1.5). One `git add .` and a push, and the key is on GitHub for good (1.3.3). `.gitignore` makes that mistake impossible *before* it happens.

## Explanation
**The order matters:**
1. Create `.gitignore` **first**, listing `.env`.
2. Then create or keep your `.env`.
3. Now `git status` won't even mention `.env`, and `git add .` won't pick it up.

**Check it:** `git check-ignore -v .env` prints which rule ignores the file, e.g. `.gitignore:1:.env  .env` (file `.gitignore`, line 1, rule `.env`).

**Commit `.gitignore` itself.** It's not secret. It's the rule book, and it should travel with the repo.

**The trap.** If a file was committed *before* you ignored it, Git keeps tracking it. Adding it to `.gitignore` changes nothing. You must also run `git rm --cached <file>` and commit. Even then, **the old commit still contains it**: `git show HEAD~1:<file>` prints it. So:

**If a real secret was ever committed:** revoke it and make a new one. If it was never pushed, stopping tracking prevents it spreading; if it was pushed, assume it's leaked. Rewriting history to scrub it is possible but advanced and error-prone; **revoking is the fix that always works**.

**A starter `.gitignore` for your projects**
```
# secrets
.env
.env.*
# personal Claude Code files (1.1.7)
CLAUDE.local.md
.claude/settings.local.json
```

## Example from your projects
`trading-research\` gets `.gitignore` as its very first file. `.env` holds `MARKET_API_KEY=...`. `git status` never shows it, the repo on GitHub never has it, and if you clone the repo onto a new PC, you create a fresh `.env` by hand.

## Hands-on exercise
**Part A: ignore a secret the right way** (in `sandbox-1.3.1`, your GitHub-backed repo)
1. `Set-Content .env "MARKET_API_KEY=fake-key-999"`, then predict and run `git status`
2. `Set-Content .gitignore ".env"`, then predict and run `git status`
3. `git check-ignore -v .env`
4. `git add .gitignore`, `git commit -m "Ignore .env"`, `git push`
5. On GitHub: is `.gitignore` there? Is `.env`?

**Part B: the trap** (a *new*, local-only repo `sandbox-1.3.4`, never pushed)
1. `cd ..`, `mkdir sandbox-1.3.4`, `cd sandbox-1.3.4`, `git init`
2. `Set-Content secrets.txt "PASSWORD=fake"`, `git add secrets.txt`, `git commit -m "Oops, committed secrets"`
3. `Set-Content .gitignore "secrets.txt"`, `Set-Content secrets.txt "PASSWORD=fake2"`, then predict: will `git status` show `secrets.txt`?
4. `git rm --cached secrets.txt`, `git add .gitignore`, `git commit -m "Stop tracking secrets.txt"`, then `git status`
5. Predict, then `git show HEAD~1:secrets.txt`

## Answers

Part B: step 3 **yes**, as `modified` (it's tracked, so the ignore rule doesn't apply); step 5 prints `PASSWORD=fake`, still in history.
