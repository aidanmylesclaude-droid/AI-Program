## What you'll learn
- How to *see* exactly what changed (`git diff`)
- How to throw away changes you haven't committed (`git restore`)
- How to undo a change you *have* committed, safely (`git revert`)

## Key terms
- **Diff:** a line-by-line comparison. Lines starting `-` were removed, lines starting `+` were added.
- **Working tree clean:** Git's way of saying "nothing has changed since the last commit".
- **Restore:** put a file back to how it was in the last commit, discarding the uncommitted changes.
- **Revert:** create a **new** commit that does the opposite of an earlier one. The bad commit stays in history, along with its undo.
- **`-a` (in `git commit -am`):** "add every *already-tracked* file that changed" before committing. It saves a separate `git add` step. New files still need `git add`.
- **Pager:** if output is long, Git shows it one screen at a time with a `:` at the bottom. Press `q` to quit.

## The problem this solves
An agent (or you) changes files and the result is worse. You need three things: to **see** what changed, to **undo** it before it's saved, and to **undo** it even after it was saved, without losing track of what happened.

## Explanation
| Situation | Command | What it does | Can you undo the undo? |
|---|---|---|---|
| "What changed?" | `git diff` | Shows uncommitted changes, line by line | Nothing to undo; it only looks |
| Changed but **not committed**, and you want the old version | `git restore <file>` | Puts the file back to the last commit | **No.** The uncommitted changes are gone for good (like `rm`). Look with `git diff` first |
| Bad change **already committed** | `git revert <hash>` (or `HEAD` for the latest) | Adds a new commit that reverses it | Yes. Both commits stay in history |

**Reading a diff**
```
--- a/notes.txt          ← the version in the last commit
+++ b/notes.txt          ← the version on disk now
-version 1               ← removed
+version 1 BROKEN ...    ← added
```

**Why revert instead of "deleting" the bad commit?** Git has commands that rewrite history (such as `reset`), but they can lose work, and they cause trouble once a repo is shared on GitHub. `revert` keeps an honest record: what went wrong and when it was fixed. For now, **revert is your undo for commits.**

`git revert --no-edit HEAD` means: revert the latest commit (`HEAD`), and use the automatic message instead of opening Notepad.

## Example from your projects
The content agent rewrites `script-07.md` overnight. In the morning: `git status` (what changed?) → `git diff` (how?) → if it isn't committed yet, `git restore script-07.md`. If it already committed it, `git log --oneline` to find the commit, then `git revert <hash>`. You keep yesterday's script, *and* a record of what the agent did.
